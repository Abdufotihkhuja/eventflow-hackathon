# REQUEST и INVITE_ONLY: типы доступа к регистрации

Краткое описание поведения режимов **REQUEST** (по запросу) и **INVITE_ONLY** (только по приглашению) и отличия от OPEN.

---

## REQUEST (по запросу)

**Суть:** Любой пользователь может подать заявку. Участие возможно только после одобрения организатором.

**Поведение в коде:**

- Событие отображается в публичном каталоге (в отличие от INVITE_ONLY).
- Регистрация без кода: пользователь нажимает «Зарегистрироваться» и заполняет форму (в т.ч. вопросы при `registrationMode === QUESTIONS`).
- Начальный статус заявки задаётся на бэкенде в `registrations.service`: при режиме QUESTIONS и `accessType === REQUEST` создаётся регистрация со статусом **PENDING** (ожидает решения).
- Организатор вручную одобряет или отклоняет заявки (методы approve/reject в `RegistrationsService` на бэкенде).

**Итог:** заявка → PENDING → организатор решает (APPROVED/REJECTED).

**На фронте:**

- Тип: `EventAccessType.REQUEST`, маппинг в `Event.access === "request"`, подпись «По запросу».
- Поле кода приглашения не показывается; `inviteCode` не передаётся в `POST .../register`.

---

## INVITE_ONLY (только по приглашению)

**Суть:** Зарегистрироваться может только тот, у кого есть действующий код/ссылка приглашения. Список участников формируется организатором через рассылку приглашений.

**Поведение в коде:**

- События с `accessType === INVITE_ONLY` **не попадают** в публичный каталог (в `public.repository` на бэкенде фильтр `accessType: { not: EventAccessType.INVITE_ONLY }`).
- У события есть поле `inviteCode` (в БД). Код можно регенерировать (старый перестаёт работать).
- Регистрация возможна только при передаче верного `inviteCode` (например, в query: `?inviteCode=...`). Без кода или с неверным кодом — 403 «Регистрация на это мероприятие доступна только по приглашению».
- Организатор может: получить ссылку и код приглашения (`getInviteLink`), регенерировать код (`regenerateInviteCode`), отправить приглашение на email (`sendInvitation` — письмо со ссылкой с подставленным `inviteCode`).
- При режиме QUESTIONS для INVITE_ONLY в `determineStatus` используется ветка «не REQUEST» → начальный статус регистрации — **APPROVED** (доп. модерация заявок не делается).

**Итог:** без кода/ссылки событие по сути «невидимо» и недоступно для регистрации; с кодом пользователь регистрируется и сразу получает APPROVED.

**На фронте:**

- Тип: `EventAccessType.INVITE_ONLY`, маппинг в `Event.access === "invite"`, подпись «По приглашению».
- На странице `/events/[slug]/register` показывается поле «Код приглашения»; при отправке регистрации передаётся `inviteCode` в query и в ссылку на `/register/questions?inviteCode=...`.

## Разница

| Критерий              | REQUEST        | INVITE_ONLY        |
|-----------------------|----------------|--------------------|
| Видимость в каталоге  | Да             | Нет                |
| Кто может подать заявку | Любой          | Только с кодом/ссылкой |
| Нужен ли код для регистрации | Нет            | Да (`inviteCode`)  |
| Начальный статус (QUESTIONS) | PENDING        | APPROVED           |
| Действия организатора | Одобрять/отклонять заявки | Раздавать ссылку/код, регенерировать код, слать приглашения на email |

**REQUEST** — открытая заявка с модерацией; **INVITE_ONLY** — закрытый список по приглашениям без модерации заявок (достаточно знания кода/ссылки).

## Связанные файлы

- Типы API: `src/shared/api/eventService.ts` — `EventAccessType`, `CanRegisterResponse.accessType`.
- Регистрация: `src/app/(public)/events/[slug]/register/page.tsx`, `register/questions/page.tsx` — проверка `accessType === "INVITE_ONLY"` для отображения поля кода и передачи `inviteCode`.
- Адаптер и подписи: `src/entities/event/lib/adapters.ts` (mapEventAccess по `accessType`), `src/entities/event/lib/formatters.ts` (accessLabels).
- Каталог: фильтр «доступ» в `events-page.tsx` и `past-events-page.tsx` учитывает `open` и `request` (события INVITE_ONLY в публичный список не приходят с бэкенда).
