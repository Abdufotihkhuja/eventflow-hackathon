# API по slug для мероприятий и блога

Используется уникальный `slug` (a-z, 0-9, дефис) для публичных URL вместо UUID.

---

## Мероприятия (Events)

### Получить мероприятие по slug (публично)

**GET** `/api/v1/events/by-slug/:slug`

- Без авторизации.
- Возвращает только мероприятия со статусом `PUBLISHED`.
- Ответ: объект мероприятия (как при GET по ID).

Пример: `GET /api/v1/events/by-slug/tech-conference-2025`

### Предложить slug по заголовку (генерация с backend)

**GET** `/api/v1/events/suggest-slug?title=...&excludeId=...`

- Требуется JWT и права `EVENTS_READ`.
- Query: `title` (обязательный, до 500 символов), `excludeId` (опционально — UUID мероприятия при редактировании).
- Ответ: `{ "slug": "tech-conference-2025" }`.

Используется та же логика, что при создании: транслитерация кириллицы, нормализация, проверка уникальности (при коллизии добавляется суффикс -1, -2, …). Удобно для подстановки в поле slug в форме до сохранения.

### Проверить доступность slug (для организаторов)

**GET** `/api/v1/events/check-slug?slug=...&excludeId=...`

- Требуется JWT и права `EVENTS_READ`.
- Query: `slug` (обязательный), `excludeId` (опционально — UUID мероприятия при редактировании).
- Ответ: `{ "available": true }` или `{ "available": false }`.

При создании вызывать без `excludeId`. При редактировании передавать `excludeId` равным ID текущего мероприятия, чтобы его собственный slug считался доступным.

---

## Блог (Blog)

### Получить статью по slug (публично)

**GET** `/api/v1/blog/by-slug/:slug`

- Без авторизации.
- Возвращает только статьи со статусом `PUBLISHED`.
- Увеличивает счётчик просмотров.

Пример: `GET /api/v1/blog/by-slug/kak-organizovat-meropriyatie`

### Предложить slug по заголовку (генерация с backend)

**GET** `/api/v1/blog-posts/suggest-slug?title=...&excludeId=...`

- Требуется JWT и права `BLOG_READ`.
- Query: `title` (обязательный, до 500 символов), `excludeId` (опционально — UUID статьи при редактировании).
- Ответ: `{ "slug": "kak-organizovat-uspeshnuyu-konferentsiyu" }`.

Та же логика, что при создании статьи: транслитерация, нормализация, уникальность.

### Проверить доступность slug (для организаторов)

**GET** `/api/v1/blog-posts/check-slug?slug=...&excludeId=...`

- Требуется JWT и права `BLOG_READ`.
- Query: `slug` (обязательный), `excludeId` (опционально — UUID статьи при редактировании).
- Ответ: `{ "available": true }` или `{ "available": false }`.

---

## Валидация slug

- Только строчные латинские буквы, цифры и дефисы: `^[a-z0-9-]+$`.
- Рекомендуемая длина: до 200 символов (events), до 200 (blog).
- При создании мероприятия/статьи slug генерируется из заголовка на backend; для подстановки в форму до сохранения используйте **suggest-slug** (по заголовку возвращает уникальный slug). Проверка через **check-slug** перед сохранением опциональна, но рекомендуется при ручном вводе slug.

# Кейсы для frontend

Ниже — типичные сценарии и какой API вызывать. Для мероприятий и блога логика одинаковая; в примерах указаны эндпоинты событий, для блога подставьте `/api/v1/blog` и `/api/v1/blog-posts`.

---

## 1. Публичная страница по slug (без авторизации)

**Сценарий:** Пользователь переходит по ссылке вида `/events/tech-conference-2025` или `/blog/kak-organizovat-meropriyatie`.

| Действие | API | Примечание |
|----------|-----|------------|
| Загрузить страницу мероприятия | `GET /api/v1/events/by-slug/tech-conference-2025` | Без заголовка Authorization |
| Загрузить страницу статьи | `GET /api/v1/blog/by-slug/kak-organizovat-meropriyatie` | Без Authorization; счётчик просмотров увеличится |

- При **404** — показать «Мероприятие / статья не найдена» (или не опубликовано).
- Не используйте UUID в публичных URL; для SEO и шаринга используйте только slug.

---

## 2. Создание мероприятия / статьи (форма организатора)

**Сценарий:** Организатор заполняет форму: заголовок, описание, slug (опционально).

### Вариант A: slug подставляется автоматически из заголовка

1. Пользователь вводит **заголовок**.
2. По debounce (например 300–500 ms) вызвать **suggest-slug** с текущим title.
3. Подставить ответ в поле slug (можно показывать как подсказку или сразу в поле).
4. При отправке формы вызывать **POST** create — backend сам сгенерирует slug из title, если не передать; если в форме есть поле slug и оно редактируемое, передать его в DTO (если API это поддерживает).

**Пример запроса suggest при создании:**

```http
GET /api/v1/events/suggest-slug?title=Tech%20Conference%202025
Authorization: Bearer <token>
```

Ответ: `{ "slug": "tech-conference-2025" }` (или с суффиксом -1, если такой уже есть).

### Вариант B: пользователь вручную правит slug

1. После подстановки из suggest или при ручном вводе — перед сабмитом (или по blur поля slug) вызвать **check-slug**.
2. Если `available: false` — показать ошибку под полем: «Этот slug уже занят».
3. Если `available: true` — разрешить отправку. При создании **excludeId не передаём**.

**Пример проверки при создании:**

```http
GET /api/v1/events/check-slug?slug=tech-conference-2025
Authorization: Bearer <token>
```

Ответ: `{ "available": true }` или `{ "available": false }`.

### Кратко по созданию

| Кейс | API | Параметры |
|------|-----|-----------|
| Подставить slug из заголовка | suggest-slug | `title` (обязательно) |
| Проверить, свободен ли введённый slug | check-slug | `slug` (обязательно), без excludeId |

---

## 3. Редактирование мероприятия / статьи

**Сценарий:** Организатор меняет заголовок или slug у существующего мероприятия/статьи.

- При изменении **заголовка** и желании обновить slug — вызвать **suggest-slug** с новым title и **excludeId** = id текущего мероприятия/статьи. Так backend не будет считать занятым slug самой этой сущности.
- При ручном вводе **slug** — вызвать **check-slug** с введённым значением и **excludeId** = id текущей сущности. Так текущий slug не покажет «занят».

**Примеры при редактировании (id мероприятия = `abc-123`):**

```http
GET /api/v1/events/suggest-slug?title=Новое%20название&excludeId=abc-123
GET /api/v1/events/check-slug?slug=novoe-nazvanie&excludeId=abc-123
```

Без `excludeId` при редактировании своё же мероприятие/статья будут считаться «занятыми» и suggest/check могут вернуть неверный результат.

| Кейс | API | Параметры |
|------|-----|-----------|
| Предложить slug при смене заголовка | suggest-slug | `title`, `excludeId` = id сущности |
| Проверить введённый slug при редактировании | check-slug | `slug`, `excludeId` = id сущности |

---

## 4. Ссылки в интерфейсе организатора

**Сценарий:** В кабинете организатора показывать ссылку «Открыть на сайте» или «Предпросмотр».

- Использовать **slug** из ответа GET по id мероприятия/статьи (поле `slug` в объекте).
- Собирать URL: `https://site.com/events/{slug}` или `https://site.com/blog/{slug}`. Для опубликованных можно вести на публичную страницу; для черновика — на превью с токеном, если такой есть в продукте.

---

## 5. Валидация на фронте (до запросов)

Перед вызовом **check-slug** или перед отправкой формы полезно проверять:

- Формат: только `a-z`, `0-9`, дефис. Регулярка: `^[a-z0-9-]+$`.
- Длина: до 200 символов.
- Пустая строка после trim — не отправлять check-slug; при create backend сам сгенерирует slug из title, если поле slug не передавать или передать пустым (в зависимости от контракта API).

При несоответствии формата — показывать ошибку под полем и не вызывать check-slug / не сабмитить форму.

---

## 6. Ошибки и граничные случаи

| Ситуация | Рекомендация |
|----------|--------------|
| suggest-slug: пустой title | Не вызывать или не показывать slug; при create backend сгенерирует из title. |
| check-slug: slug занят | Показать «Этот slug уже занят», предложить вызвать suggest-slug по текущему заголовку. |
| by-slug: 404 | Страница не найдена или не опубликована; не показывать различие по соображениям безопасности. |
| Сеть / 5xx при suggest или check | Повторить запрос или показать «Проверка недоступна, попробуйте сохранить» (backend при create всё равно проверит уникальность). |

---

## Сводка: какой API когда

| Действие на фронте | API |
|--------------------|-----|
| Открыть публичную страницу по URL со slug | **by-slug** (events или blog) |
| Подставить slug из заголовка (создание/редактирование) | **suggest-slug** (с excludeId при редактировании) |
| Убедиться, что введённый slug свободен | **check-slug** (с excludeId при редактировании) |
| Показать ссылку на мероприятие/статью | Использовать поле `slug` из ответа и собрать URL вида `/events/{slug}` или `/blog/{slug}` |

# Реализация на фронте (eventflow_client)

- **Валидация slug:** `@shared/lib` — `SLUG_VALID_REGEX`, `SLUG_MAX_LENGTH`, `isValidSlug()`.
- **События:** `publicEventsService.getEventBySlug(slug)` — GET `/v1/events/by-slug/:slug` (публично). Организатор: `eventsService.suggestSlug`, `eventsService.checkSlug`; хуки `usePublicEventBySlug`, `useSuggestEventSlug`, `useCheckEventSlug`.
- **Блог:** `publicBlogService.getBySlug(slug)` с `skipAuth: true`; организатор: `blogPostsService.suggestSlug`, `blogPostsService.checkSlug`; хуки `useSuggestBlogSlug`, `useCheckBlogSlug`.
- **Формы:** создание/редактирование события и статьи — поле slug с автоподстановкой из заголовка (suggest) и проверкой доступности (check), debounce 400 ms.
