# Регистрация на событие: кейсы и flow для Frontend

Документ описывает сценарии регистрации пользователя на мероприятие и пошаговый flow для фронтенда. Все запросы к API — с префиксом `GET /api/v1` или `POST /api/v1`. Регистрация доступна только **авторизованным пользователям типа USER** (Bearer token).

---

## 1. Используемые API

| Метод | Endpoint | Назначение |
|-------|----------|------------|
| GET | `public/events/:id` или `public/events/by-slug/:slug` | Получить событие (с вопросами и `myRegistration` при токене) |
| GET | `public/events/:id/can-register` | Проверить, можно ли регистрироваться (лимиты, дедлайн, тип доступа) |
| POST | `events/:eventId/register` | Зарегистрироваться (требуется JWT) |

Опционально для INVITE_ONLY: `POST events/:eventId/register?inviteCode=КОД`.

---

## 2. Кейсы регистрации

### 2.1. Событие без вопросов

- В ответе события: `registrationQuestions: []`.
- **Flow:** пользователь нажимает «Зарегистрироваться» → сразу отправляется `POST .../register` с телом `{}` или с опциональными полями (`role`, `travelStartDate`, `travelEndDate`, `preparationDays`).
- Ответы на вопросы не требуются.

### 2.2. Событие с уточняющими вопросами (режим QUESTIONS)

- В ответе события: `registrationMode: "QUESTIONS"`, `registrationQuestions` — массив с полями `id`, `question`, `type`, `isRequired`, `options`, `category`, `points`.
- **Flow:**
  1. Показать форму с вопросами (типы: TEXT, TEXTAREA, NUMBER, SELECT, CHECKBOX).
  2. Валидировать на фронте: все вопросы с `isRequired: true` должны быть заполнены.
  3. Отправить `POST .../register` с телом, содержащим `answers: [{ questionId, answer }, ...]`.
- Бэкенд вернёт **400**, если не ответили на обязательный вопрос (`isRequired: true`). Необязательные можно не включать в `answers`.

### 2.3. Событие с тестом (режим TEST)

- В ответе: `registrationMode: "TEST"`, `testEvaluationType` (`AUTO_REJECT` или `EVALUATION`), `minTestScore`, `maxTestScore`; у вопросов может быть `points > 0`.
- **Flow:**
  1. Показать форму как тест (вопросы с баллами).
  2. Отправить `POST .../register` с `answers` по всем тестовым вопросам.
- **Поведение бэкенда:**
  - `testEvaluationType === "AUTO_REJECT"`: если баллы < `minTestScore` → **400** «Тест не пройден...», регистрация не создаётся.
  - `testEvaluationType === "EVALUATION"`: регистрация создаётся в любом случае; баллы сохраняются в регистрации для организатора.

### 2.4. Событие по приглашению (INVITE_ONLY)

- В ответе `can-register`: `accessType: "INVITE_ONLY"`, `requiresInviteCode: true`.
- Регистрация без кода вернёт **403** «Регистрация на это мероприятие доступна только по приглашению».
- **Flow:** запросить у пользователя код приглашения, затем:
  - `POST events/:eventId/register?inviteCode=КОД` с телом (при необходимости с `answers` и др.).

### 2.5. Уже зарегистрирован

- В ответе события при запросе с токеном: `myRegistration: { id, status, eventId }` (не `null`).
- **Flow:** не показывать кнопку «Зарегистрироваться» или показывать «Вы зарегистрированы» и статус (`PENDING` / `APPROVED` / `REJECTED` / `CANCELLED`). При `APPROVED` — возможность отмены через `PATCH registrations/:id/cancel` или обновления через `PATCH registrations/:id`.

### 2.6. Регистрация недоступна

- Вызов `GET public/events/:id/can-register` возвращает `canRegister: false` и `reason` (например: «Мероприятие недоступно для регистрации», «Регистрация закрыта», «Достигнут лимит участников»).
- **Flow:** кнопку «Зарегистрироваться» отключить или скрыть, при желании показать `reason`.

## 3. Рекомендуемый flow для Frontend

### Шаг 1. Загрузка страницы события

- Запрос: `GET public/events/:id` или `GET public/events/by-slug/:slug`.
- С авторизацией: в ответе будет `myRegistration` (или `null`).

**Если `myRegistration` есть и статус PENDING/APPROVED:**  
→ Показать «Вы зарегистрированы» (и при необходимости отмену/редактирование). Регистрацию не создавать.

### Шаг 2. Проверка возможности регистрации

- Запрос: `GET public/events/:id/can-register`.
- Ответ: `{ canRegister, reason?, accessType, requiresInviteCode }`.

**Если `canRegister === false`:**  
→ Показать причину (`reason`), кнопку регистрации не показывать или сделать неактивной.

**Если `accessType === "INVITE_ONLY"`:**  
→ Показать поле ввода кода приглашения; при отправке регистрации передавать `inviteCode` в query.

### Шаг 3. Форма регистрации

- Если `registrationQuestions.length === 0`: кнопка «Зарегистрироваться» ведёт сразу на шаг 4 с телом `{}` или с опциональными полями.
- Если `registrationQuestions.length > 0`: показать форму:
  - для каждого вопроса — поле по типу (`type`: TEXT, TEXTAREA, NUMBER, SELECT, CHECKBOX);
  - для SELECT/CHECKBOX — варианты из `options`;
  - обязательность — по `isRequired`;
  - при режиме TEST можно отображать `points` у вопросов.

Опциональные поля для тела запроса (по необходимости): `role` (PARTICIPANT | SPEAKER | MENTOR), `travelStartDate`, `travelEndDate`, `preparationDays` (0–30).

### Шаг 4. Отправка регистрации

- Запрос: `POST events/:eventId/register` (для INVITE_ONLY: `?inviteCode=...`).
- Заголовок: `Authorization: Bearer <access_token>`.
- Тело (пример с вопросами и опциональными полями):

```json
{
  "answers": [
    { "questionId": "uuid-вопроса-1", "answer": "Текст ответа" },
    { "questionId": "uuid-вопроса-2", "answer": "вариант" }
  ],
  "role": "PARTICIPANT",
  "travelStartDate": "2025-06-14",
  "travelEndDate": "2025-06-16",
  "preparationDays": 2
}
```

Без вопросов достаточно: `{}` или только нужных полей.

### Шаг 5. Обработка ответа

- **200/201:** регистрация создана → показать успех, обновить состояние (например, перезапросить событие для актуального `myRegistration`).
- **400:** ошибка валидации:
  - нет ответа на обязательный вопрос → сообщение вида «Необходимо ответить на обязательные вопросы: ...»;
  - тест не пройден (AUTO_REJECT) → «Тест не пройден. Набрано X из Y баллов...».
- **403:** нет прав (например, INVITE_ONLY без верного кода или пользователь не USER).
- **404:** событие не найдено.
- **409:** «Вы уже зарегистрированы на это мероприятие».

---

## 4. Типы вопросов и формат ответа

| type   | UI              | answer в API                          |
|--------|------------------|----------------------------------------|
| TEXT   | одна строка      | строка                                 |
| TEXTAREA | многострочный  | строка                                 |
| NUMBER | число            | строка с числом                        |
| SELECT | один вариант     | строка — выбранный элемент из `options` |
| CHECKBOX | несколько вариантов | строка через запятую, значения из `options` |

Для риторических вопросов (`category: "RHETORICAL"`) можно показывать только текст (`informationalText` не приходит в публичном API); ответ обычно не отправлять или отправлять пустую строку, если бэкенд принимает.

---

## 5. Сводка по кодам ошибок регистрации

| Код | Ситуация |
|-----|----------|
| 400 | Событие не опубликовано / регистрация закрыта по дедлайну / лимит участников / не ответили на обязательный вопрос / тест не пройден (AUTO_REJECT) |
| 403 | Только для пользователей (не USER) / INVITE_ONLY без верного inviteCode |
| 404 | Событие не найдено |
| 409 | Уже есть активная регистрация (PENDING или APPROVED) |

---

## 6. Краткая блок-схема

```
Загрузка события (GET public/events/:id [с токеном])
    │
    ├─ myRegistration !== null и статус PENDING/APPROVED
    │      → «Вы зарегистрированы», не показывать форму регистрации
    │
    └─ myRegistration === null (или CANCELLED/REJECTED)
           │
           GET public/events/:id/can-register
           │
           ├─ canRegister === false → показать reason, кнопку не показывать
           │
           └─ canRegister === true
                  │
                  ├─ registrationQuestions.length === 0
                  │      → Кнопка «Зарегистрироваться» → POST register с {} или опциональными полями
                  │
                  └─ registrationQuestions.length > 0
                         → Форма с вопросами → Валидация (обязательные) → POST register с answers
                               │
                               ├─ 200/201 → Успех
                               └─ 400/403/409 → Показать сообщение об ошибке
```

Эта документация покрывает все описанные кейсы и даёт фронтенду однозначный порядок вызовов и обработки ошибок.
