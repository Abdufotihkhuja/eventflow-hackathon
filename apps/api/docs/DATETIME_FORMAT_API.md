# Формат даты и времени в API EventFlow

## Обзор

Все даты и время в API передаются в **UTC** (ISO 8601). Это устраняет зависимость от таймзоны сервера (например, при деплое в Германии) и обеспечивает одинаковую интерпретацию на фронтенде при любой геолокации пользователя.

---

## Вход (request)

### Допустимые форматы

1. **Только дата (для границ периода, дней):**
   - `YYYY-MM-DD` — интерпретируется как полночь UTC.
   - Примеры: `2025-06-01`, `2024-12-15`.

2. **Дата и время (обязательно с указанием таймзоны):**
   - С суффиксом **Z** (UTC): `2025-06-15T10:00:00Z`, `2025-06-15T18:00:00.000Z`.
   - Со смещением: `2025-06-15T12:00:00+02:00`, `2025-06-15T05:00:00-05:00`.

### Недопустимо

- Дата-время **без** таймзоны: `2025-06-15T10:00:00` — будет отклонено валидацией (400), чтобы не интерпретировать значение в локальном времени сервера.

### Где применяется

- События: `startDate`, `endDate`, `registrationDeadline`.
- Регистрации: `travelStartDate`, `travelEndDate`.
- Сертификаты: `issueDate`, `expiryDate`.
- Задачи (boards): `dueDate`, `startDate`.
- Статьи: `publishedAt`.
- Запросы с фильтром по дате: `dateFrom`, `dateTo`, `date` — можно передавать в формате `YYYY-MM-DD`.

---

## Выход (response)

Все поля типа `Date` в ответах сериализуются в **ISO 8601 UTC** с суффиксом `Z`, например:

- `2025-06-15T10:00:00.000Z`
- `2024-12-23T14:30:00.000Z`

---

## Рекомендации для фронтенда

1. **Отправка:** передавать даты в UTC (например, `date.toISOString()` или эквивалент в выбранной библиотеке).
2. **Отображение:** переводить UTC в локальную таймзону пользователя (браузер/устройство), например через `Intl.DateTimeFormat`, `toLocaleString()` или библиотеки вроде `date-fns-tz` / `luxon`.
3. Не выводить сырую строку с API без конвертации — иначе пользователь увидит время в UTC, а не в своём часовом поясе.
