# Check-in: описание, кейсы и flow для фронтенда

## 1. Обзор

**Check-in** — процесс отметки присутствия участника на мероприятии. Участник предъявляет QR-код (с билета или экрана), организатор или сотрудник сканирует его — в системе создаётся запись о посещении (attendance). Один участник может быть отмечен **один раз в день** (многодневные события — отдельный check-in на каждый день).

### Роли

| Роль                                 | Действия                                                       |
| ------------------------------------ | -------------------------------------------------------------- |
| **Участник (User)**                  | Получает QR-код своей регистрации, показывает его на входе.    |
| **Организатор / Сотрудник (Member)** | Сканирует QR, выполняет check-in, смотрит отчёты и статистику. |

### Два домена (production)

| Домен                        | Аудитория                 | Назначение                                                                                                    |
| ---------------------------- | ------------------------- | ------------------------------------------------------------------------------------------------------------- |
| **https://eventflow.uz**     | Пользователи (участники)  | Публичная афиша, поиск событий, регистрация на события, «Мои мероприятия», просмотр и скачивание билета с QR. |
| **https://app.eventflow.uz** | Организаторы и сотрудники | Дашборды, управление мероприятиями, **страница check-in**, отчёты посещаемости.                               |

**Два сценария и два base_url на бэкенде:**

| Сценарий                                                   | Кто сканирует | Куда ведёт ссылка в QR                                                            | Переменная окружения                        |
| ---------------------------------------------------------- | ------------- | --------------------------------------------------------------------------------- | ------------------------------------------- |
| **1. Один QR для всех** (на входе у мероприятия)           | Участники     | **eventflow.uz** — публичная страница check-in (например `/check-in?eventId=...`) | `FRONTEND_PUBLIC_URL=https://eventflow.uz`  |
| **2. Сканирование билета каждого участника организатором** | Организатор   | **app.eventflow.uz** — страница check-in с кодом билета (`/check-in?code=<uuid>`) | `FRONTEND_APP_URL=https://app.eventflow.uz` |

- В конфиге бэкенда: `frontend.publicUrl` (для «одного QR для всех») и `frontend.appUrl` (для QR на билете). См. раздел 8 и `.env.example`.
- QR билета (GET `/registrations/:id/qr`, PDF билета) генерируются с **appUrl**. QR «один для всех» (GET `/events/:eventId/attendance/check-in-landing-qr`) — с **publicUrl**.

### Ключевые сущности (backend)

- **Registration** — заявка на участие (с полем `qrCode`).
- **Attendance** — факт посещения: `registrationId`, `checkInAt`, `checkInDate` (уникальная пара registration + дата).

## 2. Варианты реализации Check-in на фронте

### Вариант A: Страница check-in по ссылке из QR (рекомендуемый)

- QR-код содержит URL приложения организатора, например `https://app.eventflow.uz/check-in?code=<qrCode>` (в prod).
- При сканировании открывается **страница check-in** на **app.eventflow.uz** с уже подставленным `code` в query.
- Страница доступна **только авторизованным** организаторам/сотрудникам (JWT).
- После загрузки страницы фронт может:
  - сразу отправить `POST /api/v1/attendance/check-in` с `{ qrCode: code }`, **или**
  - показать превью (название события, участник) и кнопку «Подтвердить check-in», затем отправить запрос.

**Плюсы:** один URL для всех событий, не нужно знать eventId, привычный сценарий «сканировал — открылась страница».

### Вариант B: Check-in внутри дашборда события

- В дашборде мероприятия (например `/events/:eventId/dashboard`) есть раздел «Посещаемость» с полем ввода/сканера QR.
- Пользователь вводит или сканирует код, фронт отправляет `POST /api/v1/attendance/check-in` с `{ qrCode }`.
- Backend сам определит событие по `qrCode` и проверит, что текущий пользователь имеет доступ к этому событию.

**Плюсы:** контекст «я в рамках конкретного события»; минус — участник может прийти на другое мероприятие той же организации, тогда удобно иметь и общую страницу `/check-in`.

### Вариант C: Гибрид (общая страница + виджет в дашборде)

- Общая страница `/check-in?code=...` для быстрого входа по QR с любого устройства.
- Дополнительно в дашборде события — форма/сканер для ввода `qrCode` без перехода по ссылке (например, ручной ввод или камера).

Используется один и тот же API: `POST /api/v1/attendance/check-in`.

## 2.1. Как работает сканирование билетов организатором (пошагово)

Организатор или сотрудник отмечает **каждого** участника по очереди, сканируя его билет. Есть два технических варианта; итоговый запрос к API один и тот же.

### Сценарий 1: Сканирование камерой телефона/планшета (переход по ссылке из QR)

1. **Организатор** заранее авторизован в приложении под учёткой организации или сотрудника (JWT в браузере или в приложении).
2. **Участник** подходит и показывает билет: QR на экране телефона или распечатанный билет.
3. **Организатор** открывает камеру (системную или в браузере) и наводит на QR-код участника.
4. В QR зашита ссылка вида `https://<frontend>/check-in?code=<uuid>`.
5. После распознавания QR **система/браузер** предлагает открыть ссылку (или открывает её автоматически). Открывается **app.eventflow.uz/check-in?code=...** — приложение организатора, страница check-in с уже подставленным `code` в URL.
6. **Фронт** на странице `/check-in` (на **app.eventflow.uz**):
   - читает `code` из query;
   - проверяет, что пользователь — организатор/сотрудник (иначе показывает ошибку или редирект);
   - отправляет `POST /api/v1/attendance/check-in` с телом `{ "qrCode": "<значение code>" }`.
7. **Ответ 200:** показать организатору карточку участника (ФИО, email, роль), время check-in и сообщение «Участник отмечен». После этого страницу можно очистить/обновить — готовность к следующему участнику (организатор снова сканирует следующий билет → снова переход по ссылке → тот же цикл).
8. **Ответ 4xx:** показать сообщение об ошибке (уже отмечен, не одобрен, не то мероприятие и т.д.) — см. раздел 4.

Итого: организатор **каждый раз сканирует QR участника → открывается страница с кодом → фронт отправляет check-in → показывается результат**. Для следующего участника процесс повторяется (новая ссылка с новым `code`).

### Сценарий 2: Организатор уже на странице check-in (сканер на странице или ручной ввод)

1. **Организатор** открывает в браузере приложение организатора (**app.eventflow.uz**), страницу check-in (например `/check-in` без query или раздел «Посещаемость» в дашборде события) и остаётся на ней.
2. **Участник** показывает QR или называет/показывает код (если допустим ручной ввод).
3. **Организатор** либо:
   - наводит камеру **на странице** (встроенный сканер в браузере), и фронт получает распознанный код из QR (это снова UUID из ссылки `...?code=<uuid>`), **либо**
   - вводит код вручную в поле.
4. Организатор нажимает «Отметить» / «Check-in».
5. **Фронт** отправляет `POST /api/v1/attendance/check-in` с `{ "qrCode": "<введённый или распознанный код>" }`.
6. Показать результат (успех или ошибка). Поле ввода очистить — страница готова к следующему участнику без перезагрузки.

Итого: организатор **не уходит со страницы**; для каждого следующего участника снова сканирует или вводит код и нажимает «Отметить».

### Общее для обоих сценариев

- **Кто сканирует:** организатор (или сотрудник с правом).
- **Что сканируется:** билет участника (QR, в котором зашита ссылка с `code` = UUID регистрации).
- **Что уходит в API:** один запрос `POST /attendance/check-in` с полем `qrCode` = этот UUID.
- **Результат:** один участник = одна отметка в день; при повторном скане того же билета в тот же день — 409.

## 3. API для Check-in (кратко)

- **Отметить посещение**  
  `POST /api/v1/attendance/check-in`  
  Body: `{ "qrCode": "uuid" }`  
  Нужен JWT организатора/сотрудника и право на редактирование событий (`EVENTS_UPDATE` на бэкенде).

- **QR-код для участника**  
  `GET /api/v1/registrations/:id/qr`  
  Возвращает `{ qrCode }` (base64 изображение QR). Только владелец регистрации, только одобренная регистрация.

- **Отчёт посещаемости по событию**  
  `GET /api/v1/events/:eventId/attendance?date=YYYY-MM-DD` (date опционально)

- **Статистика посещаемости**  
  `GET /api/v1/events/:eventId/attendance/stats`

- **QR «один для всех»** (ссылка на eventflow.uz/check-in?eventId=...)  
  `GET /api/v1/events/:eventId/attendance/check-in-landing-qr`  
  Ответ: `{ qrCode: "data:image/png;base64,..." }`. Для организаторов; участники сканируют этот QR при входе.

Подробно: `docs/TICKETS_API.md`, `docs/API_ORGANIZER.md`.

## 4. Кейсы и сценарии

### Кейс 1: Успешный check-in по QR (основной сценарий)

1. Участник приходит на мероприятие, открывает на **eventflow.uz** билет с QR или страницу «Мой билет» с QR.
2. Организатор открывает на телефоне/планшете **app.eventflow.uz** (страницу check-in) или сканирует QR камерой — переход на **app.eventflow.uz/check-in?code=...**.
3. На странице отображается код из `?code=...` (или сразу отправляется запрос).
4. Фронт отправляет `POST /api/v1/attendance/check-in` с `qrCode: code`.
5. **Успех (200):** показать карточку участника (имя, email, роль), время check-in и при необходимости ссылки на билеты (`ticketUrls.branded`, `ticketUrls.simple`).
6. Показать сообщение «Участник успешно отмечен» и очистить поле / подготовить к следующему скану.

### Кейс 2: Повторный check-in в тот же день

1. Организатор снова сканирует тот же билет (тот же `qrCode`) в тот же день.
2. Фронт отправляет `POST /api/v1/attendance/check-in`.
3. **Ответ 409 Conflict:** «Участник уже отмечен сегодня».
4. Фронт показывает сообщение об ошибке и, например, данные участника (из текста ошибки или из кэша, если сохраняли при первом check-in), чтобы организатор видел, что дубликат.

### Кейс 3: Регистрация не одобрена

1. Участник показывает QR билета, но его регистрация в статусе PENDING или REJECTED.
2. `POST /api/v1/attendance/check-in` → **400** «Регистрация не одобрена».
3. Фронт показывает понятное сообщение: «Регистрация не одобрена. Check-in невозможен.»

### Кейс 4: Мероприятие ещё не началось

1. QR сканируют до даты/времени начала события.
2. Backend возвращает **400** «Мероприятие ещё не началось».
3. Фронт показывает сообщение и при необходимости дату начала события (её можно получить из другого API при необходимости).

### Кейс 5: Неверный или устаревший QR-код

1. В URL попал несуществующий или чужой `code`.
2. `POST /api/v1/attendance/check-in` → **404** «Регистрация не найдена».
3. Показать: «Регистрация не найдена. Проверьте QR-код.»

### Кейс 6: Нет доступа к мероприятию (другая организация)

1. Сотрудник организации A сканирует билет участника мероприятия организации B.
2. **403** «Нет доступа к этому мероприятию».
3. Показать сообщение и не показывать детали события/участника.

### Кейс 7: Неавторизованный пользователь на странице check-in

1. Пользователь перешёл по ссылке `/check-in?code=...` без логина или под ролью «Участник».
2. Для вызова `POST /api/v1/attendance/check-in` нужен JWT организатора/сотрудника и право.
3. Фронт: если нет токена или роль не та — редирект на логин или показ «Доступ только для организаторов/сотрудников». Не отправлять запрос без авторизации.

### Кейс 8: Многодневное мероприятие

1. У события несколько дней (например 15.06 и 16.06).
2. В первый день участника отмечают — создаётся attendance с `checkInDate = 15.06`.
3. Во второй день тот же участник снова показывает тот же QR — создаётся вторая запись с `checkInDate = 16.06`.
4. Backend это разрешает (уникальность по паре registrationId + checkInDate). Фронт обрабатывает оба раза как успешный check-in.

## 5. Flow для фронтенда

### 5.1. Страница `/check-in` (вариант A)

```
[Вход]
  → Страница живёт в приложении организатора (app.eventflow.uz).
  → Читать query: code = searchParams.get('code')
  → Проверить авторизацию и роль (организатор/сотрудник)
  → Если нет доступа: редирект на логин app / сообщение «Только для организаторов»

[Если code есть]
  → Вариант 5.1.1: Сразу отправить POST /attendance/check-in { qrCode: code }
  → Вариант 5.1.2: Показать «Код: XXX. Подтвердить check-in?» → по кнопке отправить запрос

[Обработка ответа]
  → 200: показать карточку участника + «Успешно отмечен» + опционально ticketUrls
  → 400: показать сообщение (не одобрена / мероприятие не началось)
  → 403: «Нет доступа к мероприятию»
  → 404: «Регистрация не найдена»
  → 409: «Участник уже отмечен сегодня»

[После успеха]
  → Очистить code из URL (replaceState) или оставить для логов
  → Готовность к следующему скану (оставить страницу открытой или сбросить форму)
```

### 5.2. Ручной ввод кода (в дашборде события или на странице check-in)

```
[Ввод]
  → Поле ввода qrCode (или сканер камеры → распознанный код)
  → Кнопка «Отметить» / «Check-in»

[Запрос]
  → POST /api/v1/attendance/check-in { qrCode: value }
  → Тот же разбор 200/400/403/404/409, что и выше
```

### 5.3. Участник: получение QR для билета

```
[Контекст]
  → Приложение участника (**eventflow.uz**): страница «Мои мероприятия» → «Моё мероприятие» → «Билет» / «QR для входа»

[Запрос]
  → GET /api/v1/registrations/:registrationId/qr
  → Требуется: JWT пользователя, registration принадлежит ему, status = APPROVED

[Ответ]
  → { qrCode: "data:image/png;base64,..." } — это изображение QR. В QR на бэкенде зашивается URL приложения **организатора** (в prod — `https://app.eventflow.uz/check-in?code=<uuid>`, uuid = registration.qrCode), чтобы при скане организатором открывался app.eventflow.uz.
  → На eventflow.uz отобразить <img src={qrCode} />. Организатор сканирует → открывается app.eventflow.uz с code в query → фронт app отправляет POST /attendance/check-in с этим qrCode.
```

**Важно:** в body check-in передаётся именно значение из `?code=...` (UUID регистрации). Отдельно запрашивать его по API не нужно.

### 5.4. Организатор: отчёт и статистика посещаемости

```
[Отчёт по дате]
  → GET /api/v1/events/:eventId/attendance?date=YYYY-MM-DD
  → date опционально; без даты — все дни
  → Отобразить список: дата, количество, список участников с временем check-in

[Статистика]
  → GET /api/v1/events/:eventId/attendance/stats
  → totalRegistrations, totalAttended, attendanceByDate[]
  → Использовать для дашборда и графиков
```

## 6. Рекомендации по UI/UX

1. **Страница check-in** (на app.eventflow.uz): крупное поле для кода или автоматическая подстановка из `?code=...`, одна основная кнопка «Отметить», крупный блок с результатом (успех / ошибка).
2. **Ошибки:** показывать короткие, понятные сообщения (желательно на основе кода ответа и текста от backend).
3. **Повторное сканирование:** после 200 очищать форму/URL и показывать состояние «Готов к следующему участнику» (звук/анимация по желанию).
4. **Офлайн:** check-in требует запроса к API; при отсутствии сети показывать «Нет соединения» и не считать участника отмеченным до успешного 200.
5. **Права:** не показывать страницу/кнопки check-in пользователям без роли организатора/сотрудника с нужным правом.

## 7. Краткая сводка эндпоинтов

| Метод | URL                                               | Кто                   | Назначение                               |
| ----- | ------------------------------------------------- | --------------------- | ---------------------------------------- |
| GET   | `/registrations/:id/qr`                           | Участник              | Получить QR билета                       |
| POST  | `/attendance/check-in`                            | Организатор/Сотрудник | Отметить посещение по qrCode             |
| GET   | `/events/:eventId/attendance`                     | Организатор/Сотрудник | Отчёт посещаемости (опционально по date) |
| GET   | `/events/:eventId/attendance/stats`               | Организатор/Сотрудник | Статистика посещаемости                  |
| GET   | `/events/:eventId/attendance/check-in-landing-qr` | Организатор/Сотрудник | QR «один для всех» (publicUrl)           |

Все запросы — с префиксом `api/v1`, авторизация JWT. Подробные контракты и коды ошибок — в `TICKETS_API.md` и `API_ORGANIZER.md`.

## 8. Чеклист для релиза (eventflow.uz и app.eventflow.uz)

### Backend (релизная версия)

1. **CORS** — разрешить оба фронта:

   ```env
   CORS_ORIGINS=https://eventflow.uz,https://app.eventflow.uz
   ```

   Без этого запросы с eventflow.uz или app.eventflow.uz к API будут блокироваться браузером.

2. **Два base_url для QR (check-in):**
   - **QR билета** (организатор сканирует билет участника) — `FRONTEND_APP_URL=https://app.eventflow.uz`. Конфиг `frontend.appUrl`. Ссылка в QR: `https://app.eventflow.uz/check-in?code=...`.
   - **QR «один для всех»** (участники сканируют на входе) — `FRONTEND_PUBLIC_URL=https://eventflow.uz`. Конфиг `frontend.publicUrl`. Ссылка в QR: `https://eventflow.uz/check-in?eventId=...`. Генерируется эндпоинтом `GET /events/:eventId/attendance/check-in-landing-qr`.

3. **OAuth redirect** — редирект после Google/LinkedIn идёт на `FRONTEND_PUBLIC_URL`, то есть на публичный сайт `eventflow.uz` (`/auth/callback`).

### Frontend eventflow.uz (участники)

- **API** — в переменных окружения указать URL релизного API (например `https://api.eventflow.uz` или `https://eventflow.uz/api/v1` в зависимости от деплоя).
- **Билет с QR** — ничего дополнительно не нужно: QR отдаёт бэкенд (GET `/registrations/:id/qr`), в нём уже ссылка на app.eventflow.uz (при условии п. 2 выше).

### Frontend app.eventflow.uz (организаторы)

- **API** — тот же URL релизного API, запросы с app.eventflow.uz должны быть разрешены CORS (п. 1 выше).
- **Страница check-in** — реализовать маршрут `/check-in` (и при наличии `?code=...` вызывать `POST /api/v1/attendance/check-in` с этим кодом). Доступ только для авторизованных организаторов/сотрудников.
- **Авторизация** — организаторы должны логиниться на app.eventflow.uz (OAuth или логин/пароль), чтобы JWT при check-in был от организации/сотрудника.
