## 0. Сверка с реальностью (обязательное чтение перед каталогом)

ТЗ давало идеализированные state machines. Реальность (проверено по `schema.prisma` и сервисам):

| Идеализировано в ТЗ | Реальность | Решение каталога |
|---|---|---|

Отправка на модерацию = `DRAFT→PENDING_REVIEW`; reject возвращает в `DRAFT` + `rejectionReason` (`super-admin.service.ts:1983-2005`); approve возможен и из `DRAFT` напрямую (`:1915-1947`). Ещё два факта, влияющие на каналы:
- **Модератор** = `SuperAdmin` (отдельная модель), его поверхность — web-admin, где колокольчик — мок. Мобильного приложения у модератора нет → канал модераторских уведомлений: **email** (на операторов) + очередь в web-admin как счётчик (уже есть `PENDING_REVIEW`-каунты в `/stats`). Push модератору не проектируем.
- **Истечение брони билета сейчас lazy** (`expireStaleOrders` зовётся при следующем чекауте) — планировщик уведомлений (`ScheduledNotification`) станет и триггером фактической экспирации (REG-04).

## 1. Легенда

- **Каналы**: `push` (Expo), `in-app` (лента: организаторская `Notification` / новая участническая `AccountNotification`), `email`. Fallback: `push→email` — семантика **per-account**, не per-token: email отправляется, только если у аккаунта нет ни одного активного DeviceToken ЛИБО push не доставлен ни на одно устройство аккаунта (все receipts — DeviceNotRegistered/ошибка). Мёртвый токен при живом втором устройстве email-дубля не порождает (D-03б). `push+in-app` — оба всегда.
- **Приоритет**: `critical` (немедленно, игнорирует quiet hours и rate limit), `high` (немедленно, игнорирует rate limit), `normal` (rate limit + quiet hours со сдвигом).
- **Тип**: `transactional` — нельзя отключить (кроме канала push, который можно выключить на уровне ОС); `informational` — управляется `Preference key`.
- **Тайминг**: `sync` — синхронно в транзакции домен-события (через Dispatcher); `T±…` — планово через `ScheduledNotification`. TZ плановых — TZ события (`Event.timezone ?? 'Asia/Tashkent'`).
- **Dedup key** — **семантический ключ уведомления**, БЕЗ получателя и канала. Формат `{chain}:{...}`. Идемпотентность доставки обеспечивает composite unique **`(dedupKey, accountId, channel)`** на `NotificationDelivery` (DATA_MODEL_DELTA §3): fan-out на N получателей = N строк с одним dedupKey и разными `accountId`; push→email fallback = легальная вторая строка с тем же dedupKey и `channel='email'`. В колонке «Dedup key» ниже — только семантическая часть; получатель и канал добавляются composite-уникальностью автоматически и в ключ не входят. `eventVersion` = epoch-секунды `Event.startDate` на момент планирования — перенос даты меняет ключ автоматически, отдельная колонка не нужна.
- **i18n ключи** — namespace `notif.*` (mobile `strings.ts` + новый `packages/i18n/src/messages/*/notifications.ts` для веба) и `push.*` (серверные строки пуша, ru/uz/en). Email-шаблоны — существующий реестр `TEMPLATES`.
- **Preference key** — ключ матрицы `NotificationPreference`; `—` = отключить нельзя (transactional).
- **Deep link** — маршруты из инвентаря `audit/mobile.md` в **параметрической нотации Expo Router** (`/org/attendees/[eventId]`, `/ticket/[id]`) — ровно как файлы `app/**`, чтобы инвариант-тест №6 сходился с route-манифестом без нормализации; `(создать)` = маршрута ещё нет.

## 3. Цепочка 1 — Модерация события (MOD-*)

Реальная state machine: `DRAFT → PENDING_REVIEW → PUBLISHED` (approve, допустим и `DRAFT→PUBLISHED`); `PENDING_REVIEW → DRAFT` (reject c `rejectionReason`); повторная подача = снова `DRAFT→PENDING_REVIEW`. «Запрошены правки» и «отклонено» — один переход; различаем на уровне payload: модератор при reject выбирает `kind = changes_requested | rejected` (новое опциональное поле DTO, аддитивно; без него — `rejected`).

**Multi-recipient (организация).** Аудитория организаторских MOD-уведомлений: члены организации, у которых разрешение `events:update` (`PERMISSIONS.EVENTS_UPDATE`, `permissions.constant.ts:11`; резолв через `OrganizationRole`→`RolePermission` + персональные `MemberPermission`), плюс владелец всегда. In-app строка остаётся организационной (`memberId=null` — видна всем, как сейчас); **push** фанаутится только на устройства аккаунтов отфильтрованных членов (через `Membership → Account → DeviceToken`). Так лента не шумит, а звонит только тем, кто может действовать.

**Анти-спам при повторной подаче.** Per-переход, без агрегации (объёмы модерации малы — единицы в день, см. каунты `/stats`): (а) dedup-ключ модераторской очереди включает счётчик подач `submitSeq` = число предыдущих `PENDING_REVIEW`-подач события (новая колонка не нужна: считается count'ом `NotificationDelivery`-строк по префиксу `mod:queue:{eventId}:`); без `submitSeq` resubmit в те же 10 минут после reject дедупился бы как дубль исходной подачи — модератор не узнал бы о повторной подаче (D-12); (б) модераторский SLA-таймер (MOD-03) при повторной подаче создаётся заново, старый отменяется; (в) rate limit цепочки: не более 1 push MOD-01 организатору в 10 минут на событие (защита от submit/undo-дребезга) — реализуется тем, что dedup-ключ квантуется 10-минутным окном.

## 4. Цепочка 2 — Прогресс регистрации (REG-*)

Реальная машина: `Registration.status: PENDING → APPROVED | REJECTED`, `→ CANCELLED` (терминальный; организаторский cancel и revoke→PENDING — см. память проекта и E-10/E-11). Платное плечо: `Order(TICKET_SALE): PENDING_PAYMENT --15м hold--> PAID | EXPIRED`, `PAID → REFUNDED` (возврат — managed-фаза, оператор). Билет: `ticketIssuedAt` + `TicketArtifact` (QR, офлайн-доступен на `/ticket/[id]` — экран уже рендерит билет из кэша). Check-in: строка `Attendance`.

**Скоуп Order-цепочки (B-05).** Полный enum `OrderStatus` содержит ещё `REQUESTED` — и это `@default` (`schema.prisma:2396-2432`); Order — общая модель с биллингом. Все guard'ы, `cancelBy({orderId})` и точки эмиссии Order-плеча (REG-02..05, REG-12, REG-23) **явно фильтруют `kind=TICKET_SALE`** — биллинговые заказы других kind цепочка не читает и не отменяет.

## 5. Цепочка 3 — Напоминание об событии (REM-*)

Триггер: `T_start − offset` в TZ события (`Event.timezone ?? platformDefault('Asia/Tashkent')` — новая nullable-колонка; обоснование: платформа UZ-only, но ONLINE/HYBRID-события уже есть в `EventFormat`, и абсолютный UTC-расчёт сломается на первом же зарубежном онлайн-событии; nullable + платформенный дефолт не требует бэкфилла).

**Offset-политика конфигурируема без хардкода**: `ScheduledNotification` создаётся из таблицы офсетов `REMINDER_OFFSETS = [{key:'24h', minutes:1440}]` (платформенный конфиг `PlatformSetting`, прецедент есть); добавление `1h`/`1w` — правка конфига, планировщик пересобирает недостающие job при ежедневном reconcile-свипе.

- **Аудитория**: регистрации `status=APPROVED` (реальный «подтверждён»). PENDING-заявки — НЕ включаем (человек не подтверждён организатором; уведомление «вы всё ещё в ожидании» — другой жанр, OPEN-Q-06). Waitlist не существует.
- **Содержимое**: время в TZ события, площадка (`venue`, `address` есть; deep link на карту — маршрут `/map` существует, `latitude/longitude` у Event есть; параметры маршрута — проверить при реализации), QR-билет (`/ticket/[id]`, офлайн), правила входа (статического поля «правила входа» у Event нет → в пуше только формат ONLINE/OFFLINE + ссылка `onlineUrl` для онлайна; OPEN-Q-07).
- **Событие создано/опубликовано < 24h до старта**: если `T_start − now < offset`: при `T_start − now ≥ 2h` — отправить немедленно (регистрация свежая, но напоминание с QR всё равно ценно); при `< 2h` — skip (участник только что регистрировался, билет на руках). Правило применяется и к поздним регистрациям на давно опубликованное событие.
- **Quiet hours**: плановое время попадает в 22:00–08:00 локали события (напр. старт в 02:00 → reminder в 02:00 предыдущих суток) → сдвиг ВПЕРЁД на ближайшие 08:00, но не позже `T_start − 2h`; если и это невозможно — шлём в исходное время (лучше ночной пуш, чем пропущенное событие: transactional-примат).

## 8. Кросс-цепочные инварианты (все 7, с механизмами)

1. **Идемпотентность по dedup_key.** Таблица `NotificationDelivery` с composite unique **`(dedupKey, accountId, channel)`** (DATA_MODEL_DELTA §3): `dedupKey` — семантический ключ уведомления, получатель и канал — отдельные колонки уникальности. Диспатчер делает `INSERT` строку на каждого получателя×канал; `P2002` (unique violation) = эта доставка этому получателю по этому каналу уже была → noop с логом `notification.deduplicated`. Fan-out на N получателей даёт N строк — никто не подавлен; push→email fallback — легальная вторая строка с `channel='email'` (дефект B-04 закрыт). Redis-дедуп почты остаётся вторым эшелоном (канальным), но истина — БД: переживает Redis flush и краш между reserve/send (закрывает дыру аудита «письмо потеряно молча»: строка в статусе `enqueued` без `sent` видна reaper-у).
2. **Единая точка NotificationDispatcher.** Все пуши/письма/in-app цепочек идут через `NotificationDispatcherService.dispatch(intent)` в `apps/api/src/modules/notifications/`. Прямые вызовы Expo push из фич запрещены ESLint-правилом — по образцу существующего tenant-правила (`apps/api/eslint.config.mjs:64-73`, `no-restricted-syntax` + ratchet-скрипт `scripts/check-tenant-guard.mjs`): новое правило `no-restricted-imports` уровня **error**: `{ paths: [{ name: 'expo-server-sdk', message: 'Push только через NotificationDispatcher (modules/notifications). Прямые вызовы запрещены.' }] }` для `src/**`, с `ignores: ['src/modules/notifications/**']`; плюс `no-restricted-syntax` селектор `NewExpression[callee.name='Expo']` там же. Ratchet-скрипт `scripts/check-notification-dispatch.mjs` (клон tenant-ratchet'а) держит error-уровень в CI.
3. **Каскадная инвалидация jobs.** Все плановые уведомления — строки `ScheduledNotification` с индексируемыми `eventId`/`registrationId`/`orderId`. Смена `Event.status` на CANCELLED, перенос `startDate/endDate/registrationDeadline`, `Registration→CANCELLED/REJECTED`, `Order (kind=TICKET_SALE)` из PENDING_PAYMENT — вызывают `scheduler.cancelBy({eventId|registrationId|orderId, reason})` В ТОЙ ЖЕ транзакции, что и смена статуса (прямой вызов сервиса — по действующей архитектуре без event-emitter'а). Второй эшелон: каждый job перед отправкой перечитывает guard-условие (актуальный статус) — отмена, пришедшая между планированием и исполнением, не проскочит.
4. **Rate limit.** Redis sorted-set `push:rl:{accountId}` (score = timestamp), скользящее окно 1h, cap **4 informational-пуша/час** на пользователя; `transactional` и `critical/high` идут мимо лимита. Превышение → delivery в статус `suppressed_rate_limit` (виден в админ-диагностике), для CLS-канала — приоритет по ближайшему дедлайну. Плюс суточный cap категории `saved_event_alerts` = 1 (см. CLS-01).
5. **Все шаблоны ru/uz/en, отсутствие ключа = fail CI.** Единый машинный каталог `apps/api/src/modules/notifications/catalog.ts`: для каждого ID из этого документа — `{ id, pushKey, inAppKey?, emailTemplate?, deepLink }`. CI-тесты: (а) в `apps/api` — для каждого `emailTemplate` реестр `TEMPLATES` содержит билдер и его вызов с тремя локалями возвращает непустые subject/body (у `L()`-хелпера все три ветки обязательны); (б) в `apps/mobile` — jest-тест итерирует `pushKey`/`inAppKey` каталога (импорт по workspace-пакету или сгенерированный JSON-снапшот) и проверяет наличие ключа в `strings.ts` для `uz|ru|en`; (в) в `packages/i18n` — тот же тест для веб-словаря `notifications.ts`. Любой отсутствующий ключ → красный CI.
6. **Валидный deep link у каждого пуша.** Тест в `apps/mobile`: route-манифест строится из файловой структуры `app/**` (тот же источник, что typedRoutes; статический glob в тесте), каталог даёт `deepLink.route` в параметрической нотации Expo Router (`/org/attendees/[eventId]` — как имена файлов) — каждый route обязан существовать в манифесте, сравнение прямое, без нормализации; несуществующий → fail. Маршруты, помеченные в каталоге «(создать)», включаются в манифест-тест только после создания (до того — allowlist `PENDING_ROUTES` c комментарием-тикетом, чтобы тест не блокировал бэкенд раньше мобилки).
7. **Tenant isolation при построении получателей.** Все recipient-builder'ы (`resolveOrganizerAudience(eventId)`, `resolveAttendeeAudience(eventId)`, `resolveInterestedAudience(eventId)`) живут в repository-слое модуля notifications и обязаны использовать `requireTenantWhere()/requireEventTenantWhere()` (`src/common/tenant`) — уже существующий механизм 0.4 с ESLint-нюджем и ratchet-скриптом; сырые Prisma-обращения к tenant-моделям вне repository ловятся действующим правилом (`eslint.config.mjs:64`). Аудитории строятся строго от `eventId → event.organizationId` из БД, никогда из ввода (паттерн текущих emit-точек, `audit/backend.md` «Изоляция»).
